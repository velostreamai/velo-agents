# Scope — PR #2152 (#2149), round 1

**First foreign-model review of this PR.** It is green locally and in CI, and on this issue family green has never been sufficient: the original field-order bug was found by an ad-hoc flake probe, not by the 11.8k-test suite, and #1918's two P1-class defects were both found by reading while the suite was green.

**You did not author this.** The implementation was written by glm; the two gate fixes by sonnet; the `/check-code` pass was the orchestrator's. You are the first reviewer independent of all three.

## What it does

`JoinLayout::from_existing_multi_source_fields` copied its seed slice verbatim with no dedup, so a duplicated qualified field name produced two byte-identical `LayoutEntry` structs — and every consumer that iterates `entries()` into an output `Vec` emitted **two columns where one was intended**. #2145 guarded three of eleven call sites individually; this closes the class inside the constructor.

6 commits: the constructor dedup, 9 tests, then two gate fixes (removing the now-redundant caller-side dedup wrappers; rewriting docstrings that recounted review history), plus two `cargo fmt` commits.

## Attack these

**A1 — is the dedup actually unreachable-by-omission now?** The whole argument for constructor placement is that a caller cannot miss it. Verify there is no *other* path that builds `JoinLayout` entries from a seed without going through `from_existing_multi_source_fields` — check `from_sides`, `extend_with_right`, `append_relation`, `shadow_or_append`, and `BatchLayout::from_sides` (a DIFFERENT type, `join/coordinator/mod.rs`, which `layout.rs:47-51` documents as still emitting duplicate `t.x` entries). If a sibling constructor can still produce duplicate entries, the class is not closed and the PR's central claim is overstated.

**A2 — the gate fix F1 removed three caller-side `dedup_seed_fields` calls** at `processors/join.rs` (`merge_join_records_with_aliases`, `combine_records_with_nulls`, `combine_records_with_nulls_for_probe`), on the premise that the constructor dedup is exactly equivalent. **Verify the seeds at those three sites flow ONLY into `from_existing_multi_source_fields`** and are not also used, un-deduped, for anything else in the same function — an output field vector, a length, an index map. If a seed is reused after the call, removing the wrapper silently reintroduces the duplicate downstream. This is the single highest-risk edit in the PR.

**A3 — first-wins vs last-wins is claimed unobservable.** The argument: every consumer resolves a Left-side entry's value by field NAME, a pure function of `(record, name)`, so which duplicate survives changes only position. Test that independently against the 8 enumerated consumers. A consumer that resolves by INDEX, or that pairs `entries()` positionally against a separately-built array vector, would break the claim.

**A4 — `BatchLayout::from_sides` panics** via `assert_eq!(order.len(), n_data)` on a duplicate seed (`join/coordinator/mod.rs`). The PR calls this "fail-loud". Confirm the constructor dedup actually prevents that panic being reachable rather than merely making it rarer, and that no test now depends on the panic.

**A5 — test cardinality, not just presence.** 9 tests claim one per affected consumer plus a sweep. The tests assert a name appears exactly once. Check they would fail for the RIGHT reason — i.e. they observe emitted column count, not merely that a lookup succeeds. A test asserting `count == 1` against a map-based lookup would pass even with duplicate emission.

## Do not report

- **Whether dedup belongs in the constructor.** Pinned by the orchestrator, with the reasoning in the PR body. A fix depending on a complete caller list has already failed twice on this exact function.
- The `FxHashSet`-per-call allocation in `dedup_seed_fields` — known, documented in the PR as out of scope, and not a regression (the #2145 baseline already paid it).
- Style, naming, comment density, docstring length.
