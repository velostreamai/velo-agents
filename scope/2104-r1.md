# Scope — PR #2104, review round 1

## What this PR is
#1918: unaliased computed SELECT items were all named `__expr__` and unaliased
GROUP BY keys `__group__`, producing duplicate, unreferenceable output field
names. Both output-naming sites now route through one helper,
`schema_propagation::output_name_for_select_expr`, which names an unaliased
non-column expression `EXPR$<n>` by its zero-based position in the SELECT (or
GROUP BY) list. `output_name_for_column_ref` moves from `builder.rs` to
`schema_propagation.rs` so both sites share it.

## Provenance — read this, it determines where to look
Written by a codex dispatch that **stopped with the work uncommitted**, then
finished inline by the orchestrator. That split is the risk surface:

- The worker's three tests were written under names that did **not** match the
  spec's declared `fail_to_pass` list. The orchestrator renamed them. A rename
  driven by a name list is exactly the kind of change that can make a test's
  name describe more than its body proves.
- The third declared name,
  `plan_schema_and_project_exprs_agree_on_unaliased_expression_names`, asserts an
  *agreement between two surfaces*. The worker's test exercised only
  `schema_from_select_fields`. The orchestrator rewrote the body to drive both
  surfaces. **That new test is orchestrator-written and has had no independent
  review.** It is the single highest-value thing to attack in this PR.
- The worker deleted a comment block when moving `output_name_for_column_ref`.
  The orchestrator restored it from the pre-move source. Verify the restored
  text still describes the code it now sits above, rather than the call site it
  was written for.

## The trap the orchestrator already found — calibrate against it
The obvious way to write the agreement test is to compare the `Project` node's
expr names against `plan.schema` field names. **That test is vacuous**:
`output_schema`'s `Project` arm does `Arc::clone(alias)` on the name the builder
already computed, so the comparison holds no matter how badly the two generators
diverge. The orchestrator avoided it by driving `schema_from_select_fields`
directly from the same parsed SELECT list.

Assume there is a second instance of this class in the PR. Every assertion in
all four tests should be checked for whether it can fail at all. An assertion
that cannot fail is a P1 here, because the entire value of this PR is that two
independent naming paths agree, and a test that cannot detect divergence
re-opens the defect silently.

## Your job this round
1. **Can the two naming paths still diverge?** `select_fields_to_project_exprs`
   (builder.rs), `schema_from_select_fields` (schema_propagation.rs) and
   `expr_output_name` (GROUP BY) all claim to route through one helper. Verify
   from the code, not the PR body. Any remaining private naming decision — an
   early return, an alias short-circuit, a wildcard arm, a `SelectField` variant
   handled before the helper is reached — is a finding. `SelectField` has four
   variants; confirm each is named identically by both paths or explain why the
   difference is correct.
2. **Positional naming under composition.** `EXPR$<n>` is positional. What
   happens when the SELECT list contains a wildcard before a computed item — does
   `n` count the wildcard? Is the schema side's `filter_map` (which drops
   wildcards) enumerating before or after the drop? A position skew between the
   two sides would produce names that agree in the tests and disagree in
   production. This is the most likely real defect in the PR; derive it from the
   code.
3. **Attack the orchestrator-written agreement test.** Can it pass while the two
   generators disagree? What does it prove about `t.amount` that the builder-only
   test does not? Would it catch a regression that reverts
   `schema_from_select_fields` to `__expr__`? Would it catch one that reverts
   only the qualifier strip?
4. **Collision non-handling is deliberate** (#1919 owns it). Confirm nothing in
   this PR silently renames, suffix-bumps, or dedups. A generated `EXPR$0` that
   collides with a user column literally named `EXPR$0` must pass through
   unchanged; verify it does, and that no test asserts the opposite.
5. **Hot-path check.** `output_name_for_select_expr` is called per SELECT item at
   plan time. Confirm it is plan-time only and did not get pulled onto a
   per-record path. The `format!("EXPR${position}")` allocation is acceptable at
   plan time and would not be per record.
