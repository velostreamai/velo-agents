# Scope — PR #2152 (#2149), round 2

**Round 1 blocked this PR on a P1.** This round reviews the fixes, scoped to the delta since `89dc5db8f`.

Round 1 history, because it sets the bar: two gates ran. One returned *approve-with-findings* after real work (it cloned the worktree, ran a mutation, found more failing tests than the author reported) and **missed a P1 silent-wrong-output regression** that the other found by reading. Its consumer audit concluded "every consumer resolves by name"; the one consumer that derived a column count by *subtraction* was never in its list. The orchestrator's own review missed it for the same reason.

Then the fix round found a **second member of the same class**, in production, worse than the first.

The pattern across all three defects in this family is identical: **a value derived from one authority, checked against another.**

## Attack these

**B1 — is the class actually closed now?** Two members were found and fixed; the sweep claims exactly two. **Re-derive it independently.** The shape is: any value describing the JOINED batch computed from the probe and/or build inputs rather than from the joined batch. That includes counts, capacities, slice bounds, index comparisons and loop ranges — not just subtractions. Search beyond `sql/execution/` if the shape can occur elsewhere. A third member is the single most valuable thing you can find; two rounds have each found one.

**B2 — `probe_build_data_split`'s sentinel scan.** It takes the first data column whose name starts with `"__vs_build__"` followed by `'.'`. Verify: can a *probe* column legitimately carry that prefix (making the split too early)? Can a build column *fail* to carry it (making the split too late)? Is `BUILD_COLUMN_SENTINEL` guaranteed applied to every build column on every path reaching this function, including outer-join NULL-fill and the empty-build-side early return? The `unwrap_or(n_data)` fallback silently means "no build columns" — confirm that is right rather than masking a missing prefix.

**B3 — P1b at `:743` deviates from the pinned fix, by the author's own report.** The brief said use `joined.field_count()`; no `joined` exists at that call site, so it used `layout.len()`, arguing they are equal by construction because `build_take_combine_schema_and_layout` builds the schema's data prefix by iterating `layout.entries()` 1:1. **Verify that equality independently.** If the layout can ever carry an entry that does not become a data column (or vice versa), `:743` is wrong — and it is the test-only helper, so a wrong value there weakens every test that uses it while looking green.

**B4 — the P3 fix applies a `contains('.')` branch to `interval_join.rs`'s schema selection to match `BatchLayout`.** That is the same heuristic the #2138 retraction called out as "a heuristic standing in for a provenance check it never performs". Verify the two sides now genuinely agree for every input shape, not merely for the tested one — in particular a left source with a dotted field name where the dedup changes nothing, and a schema with dotted names that are all unique. Does the assert at `coordinator/mod.rs:6503` still catch what it was written to catch (the `#1833` aliased-schema gap)?

**B5 — the doc correction claims a prior safety argument was false.** `dc33b1165` corrects a comment that claimed release builds "fail loudly anyway via `RecordBatch::try_new`", on the grounds that the same wrong value feeds both the field-list build and the array gather, so arity stays internally consistent. **Verify that reasoning** — it is the justification for why this defect was silent rather than loud, and the same claim has now been invalidated twice (once by #2146's gate). If any path does still get a loud failure, the corrected doc is now wrong in the other direction.

**B6 — red-first evidence.** Each fix claims a test observed failing first, with quoted output. Spot-check that the tests as committed would still fail against their defect — in particular that `take_path_projection_preserves_...` fails for the *system-column drop* and not incidentally via some other assertion, and that the full-column-list assertions at the three `processors/join.rs` sites pin order as well as membership.
