## Attack these, in order

1. **R7's guard, `group_by.rs` / `flush_group_by.rs`.** The loop emits
   `output_name_for_group_expr(group_expr, slot)` — `GROUP$<n>` for a computed
   key — and the #1323 duplicate guard previously compared against the raw
   `col_name`, so it never fired for computed keys. Verify the fix compares the
   emitted name, and that it still fires for the bare-column case it was
   originally written for (`#1322`/`#1323`). Over-firing would DROP a legitimate
   second name (`symbol AS s`), which is the opposite defect.

2. **The 44-line deletion in `group_by.rs`.** An earlier round added a JOIN-scoped
   `duplicates_group_emission` special case, then deleted it. Confirm the deletion
   restored the prior behaviour rather than leaving a third state — in particular
   that the non-JOIN columnar byte-parity contract
   (`group_by_columnar_parity_test`) still holds, since that contract deliberately
   pins the duplicate push on both paths.

3. **R6's orphan-slot path in `builder.rs` / `schema_propagation.rs`.** Round 2
   established it is not parser-reachable except through a nested-aggregate gap.
   The delta touched `builder.rs` again — confirm that is still true.

4. **The 12 new tests: do they actually reach their paths?** This is the highest
   value question, because the whole issue's history is tests that passed while
   testing nothing. Specifically:
   - `ctas_registers_positional_names_for_unaliased_computed_items` — does it
     assert the **registered** schema, or only a locally-propagated one? Only the
     registered form persists for later queries.
   - `having_binds_over_an_unaliased_computed_aggregate` — does it assert the
     **filtered value**, or only that a name exists?
   - `lifted_aggregate_inside_case_with_group_by_names_one_field` — is the
     aggregate genuinely INSIDE the CASE (lifted), not a direct aggregate with a
     CASE in its argument? The audit found an existing test that looked like this
     shape and was the other one.
   - `mixed_direct_and_lifted_aggregates_in_one_query_name_one_field_each` —
     `SELECT SUM(a), SUM(b) + SUM(c)` must exercise BOTH the owned and lifted
     paths; if it only reaches one, it does not pin what it claims.

5. **`RED-FIRST` honesty.** `agent.log` carries a `RED-FIRST` line per
   `fail_to_pass` test. One deviates and says so: R7's test was proved red at the
   **pre-fix branch HEAD**, not at `origin/master`, because master cannot reach
   that guard path through `PrimedQuery` priming. Judge whether that baseline is
   legitimate for a defect introduced earlier in this same branch.

## Do NOT re-report

  called it a P1 write/read mismatch; `check-code` refuted it by tracing
  `walk_expr_for_aggs → agg.alias → resolve_aggregate_key`, establishing the
  aggregate read key derives from the AST alias and never `alias_keys`. Ten
  passing `differential_test` group-key shapes corroborate. Round 2 confirmed the
  per-row allocation was moved into the `Aggregate(_)` arm as briefed.

  deliberately: an external test crate pins the legacy strings, so `pub(crate)`
  would break it and deleting the test is forbidden. It carries `#[doc(hidden)]`
  and a justification.
- A user column literally named `EXPR$0` — unconstructible, `$` is not admitted in
  bare identifiers. Deferred to #1919.
