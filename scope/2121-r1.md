unaliased computed expression carries the same name in the plan schema AND the

## The one thing that can be silently wrong

`PlanNode::Aggregate::alias_keys` is **not only an output name** — it is the key
the runtime aggregate evaluator looks up. `walk_expr_for_aggs` says so:
the alias "matches the key the runtime evaluator uses for lookup, so write and
read sides agree."

So a half-migration does not fail a test. It produces **wrong output**: the plan
writes one key, the runtime reads another, and an aggregate silently resolves to
the wrong slot or to nothing. Earlier in this issue a one-sided edit to
`build_plan_alias_keys` failed 48 tests — but that was the *lucky* case, where
coverage existed. Assume the unlucky case exists somewhere in this diff.

`ALIAS-KEYS | mode=migrate` is logged. Verify the migration is complete and
atomic, not that the log says so.

## Your job this round

1. **Trace one aggregate end to end, in code, not in tests.** Pick
   `SELECT SUM(value) FROM t GROUP BY k`. Follow the name from
   `build_plan_alias_keys` → `PlanNode::Aggregate::alias_keys` →
   `output_schema`'s Aggregate arm → the runtime read in
   `processors/select/group_by.rs` and `group_by_columnar.rs`. Do the write key
   and the read key agree at every hop? A single hop where one side says `EXPR$0`
   and the other says `__agg__` or `SUM(value)` is a P1.
2. **`get_expression_name` and `generate_field_name` are demoted to "lookup
   keys".** Confirm neither can still reach a `Schema` or an emitted record field
   name on ANY path — including `interval_join.rs`, `rows_window.rs`,
   `window_projection_operator.rs`, and the flush/emit paths. A demotion that
   leaves one escape route is the defect this PR claims to close.
3. **`__agg__` / `UNNAMED_AGGREGATE_PLACEHOLDER` still exists in `builder.rs`.**
   That is intended — it is the internal slot key. Verify it cannot reach a plan
   schema or a record. If it can, bar 2 is unmet.
4. **The 34 expectation changes.** Only two edit shapes are permitted inside a
   pre-existing test: a legacy generated-name literal becoming
   `EXPR$<n>`/`GROUP$<n>`, or a qualified output name losing its qualifier.
   **Sample at least 8 of the 34** and check the `CHANGED-EXPECTATION` rationale
   in `agent.log` against the actual hunk. I verified mechanically that no
   assertion was deleted and no `#[ignore]` added; I did NOT verify that each
   rationale is *true*. A rationale that misdescribes its hunk is a finding.
5. **`GROUP$<n>` collision reasoning.** The claim is that two positional counters
   in one namespace would collide for
   `SELECT COUNT(*) FROM t GROUP BY price * quantity`, because `output_schema`
   appends group fields before aggregates. Verify that from the code. If the
   premise is wrong, `GROUP$<n>` is unnecessary complexity and should be one
   namespace.
6. **Hot path.** These names are built at plan time. Confirm nothing moved onto a
   per-record path — in particular no `format!("EXPR${}", ...)` per row, and no
   per-record `HashMap` lookup introduced where an index existed.
