## What it does

Four join record-construction sites built an **ordered** `JoinLayout` and then poured it into an `FxHashMap`, letting hash iteration decide the emitted column order. Two of the four carry docs promising a specific physical layout. They agreed only by accident: `FxHash` is seed-free and all four shared a key set.

That accident has broken before — `columnar/adapter.rs::batch_to_records` had the identical defect, its doc promising schema order while a map decided it, and #1918's rename perturbed the hashes and surfaced it. It was found by an ad-hoc flake probe, **not** by the 11.8k-test suite.

## Attack these

**A1 — did dropping the map change emitted CARDINALITY, not just order?** This is the highest-value question and it is the one that bit #2146 repeatedly. An `FxHashMap` also *collapses duplicate names*; `build_batch` does not — it pushes every pair. So a lazy iterator emits two columns where the map emitted one.

The spec argues this cannot happen because `layout.entries()` names are unique by construction: `append_relation` routes **every** entry through `shadow_or_append`, which dedups against `name_pos`; `from_sides` seeds a fresh map; `extend_with_right` seeds from the left. Therefore a duplicate requires the slice handed to `from_existing_multi_source_fields` to already hold one — and that slice is a prior level's own output.

**Verify that induction independently.** Note two distinct types have a `from_sides` (`JoinLayout` at `execution/join/layout.rs:168`, `BatchLayout` at `execution/join/coordinator/mod.rs:6450`) and `layout.rs:47-51` documents the *latter* as still emitting duplicate `t.x` entries. Confirm the diff does not touch a path where that matters.

**A2 — is the pinned form actually allocation-free?** The spec requires a lazy iterator, forbidding an intermediate `Vec`. Check each of the four sites takes an iterator and that `build_batch` consumes `impl IntoIterator` in a single pass without needing `len()`. Also confirm site 651 uses `from_explicit_with_key` (`builder.rs:896`), not `from_explicit` — the doc bar covers both.

**A3 — `pack_join_results` order stability.** It builds emitted column order as the union across **all** rows by first occurrence (`join_dispatch.rs:535-543`: a `col_order` Vec guarded by a `seen_cols` FxHashSet). On the stream-stream path two producers feed one `output_rows` vec with *different* orders — take-combine via `BuildSideStorage::new` (Arrow-schema order) and site 933 (`FxHashMap` order). Does converting 933 change which order wins, and does the query-level assertion actually pin that? A site-level test passes while the query-level order stays unpinned.

**A4 — the red-first proof.** `join_emits_columns_in_layout_order_under_adverse_hash_order` had to FAIL at the pinned base `ce56ad5be`. Check `agent.log` carries a `RED-FIRST` line with the real assertion text, and that the test is registered in the parent `mod.rs` (an unregistered test file is never compiled, so it cannot fail).

**A5 — per-row identity.** Egress-adjacent change. Confirm no `*_at(row_index)` call site is touched and that no system column (`_offset`, `_key`, `_headers`, `_traceparent`, `_event_time`) changed position or was dropped.
