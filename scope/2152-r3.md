## Attack these

**D1 — the new guard's placement and cost.** `reject_probe_field_carrying_build_sentinel` runs at the top of `probe_stream_stream_batch`, i.e. **per batch on a hot path**. It iterates `probe.data_field_names()` and prefix-tests each. Assess: is `data_field_names()` cheap here or does it allocate/clone per call? Is per-batch the right frequency, or is this a plan-time property that should be validated once per schema generation? A validation that cannot fail for a given schema but re-runs per batch is the hot-path pattern this repo treats as a defect.

**D2 — is the guard complete?** It checks `probe.data_field_names()`. Enumerate what else reaches `probe_build_data_split`'s scan: can a **build** field carry the sentinel prefix and survive (the prefix is applied to build fields deliberately, so a build field named `__vs_build__.x` becomes `__vs_build__.__vs_build__.x` — does anything mis-strip)? Is `probe_stream_stream_batch` the only entry point to the take-combine path that reaches the split, or can another caller reach it unguarded? The round-2 defect existed because a guard was placed where it could be bypassed; verify this one cannot.

**D3 — does the guard fail loud in the right way?** It returns `Err(SqlError::execution_error(...))`. Confirm the error propagates to the operator boundary rather than being swallowed, and that it does not convert a previously-working query into a hard failure. A source column genuinely named `__vs_build__.something` is pathological, but if one exists today this change breaks that job — is that the intended trade, and does the message tell the operator what to do?

**D4 — R2's new test reaches production, verify it.** The claim is that it drives the interval-join construction through `plan_source_schemas` rather than re-implementing the branch predicate, and that reverting `interval_join.rs:231` makes it fail (quoted panic: `derived row schema length 7 does not match arrow data column count 8`). Verify it genuinely reaches the production dispatch and does not reconstruct any part of the decision itself. Note the author's refinement: a single **non-duplicated** dotted field suffices, because the dotted branch always adds one fewer `_EVENT_TIME` entry than an unconditional merge regardless of duplication — check that reasoning.

**D5 — R1's doc, third attempt.** The original text was wrong; the round-2 correction overshot in the other direction; this is the third version. Read it and confirm it now states the production behaviour accurately (panic in `from_batch` on the first affected batch, because `_event_time` is `is_required()` and first in canonical order) and that the "silent" characterisation is scoped only to `ensure_projection_layout_for_test`.
