First review of this PR. Nothing here has been gated before.

## What it does

`SELECT` could emit two columns under one output name — silently. On any egress
path that materialises a field map the second overwrote the first, so a selected
column vanished on write. #1918 made generated names unique and referenceable;
this makes the *collision* a validation error (`[NB-005]`) instead of a silent
merge.

## The two orchestrator rulings this PR encodes

The worker STOPped twice rather than touching existing tests. Both rulings are in
`.agents/tasks/1919-brief.md` §4z and §4y and on the issue. **Judge the rulings,
not just the compliance** — they were written by the orchestrator, and a reviewer
who only checks "did it do what it was told" cannot catch a wrong instruction.

**Ruling 1** — NB-001 (does the input *resolve*?) must be checked BEFORE NB-005
(are the *output names* unique?), reporting whichever fires first.

**Ruling 2** — NB-005 stays **universal**, not narrowed to CTAS/CSAS. This is a
deliberate divergence from Postgres/MySQL/DuckDB/Flink, which accept duplicate
output names in a plain `SELECT` and reject them only for `CREATE VIEW`/CTAS. The
stated reason: in a streaming engine a `SELECT`'s output is a materialised stream
bound by name downstream, so a duplicate is unreferenceable with or without a
`CREATE` wrapper.

## Attack these

**A1 — the ordering is a correctness claim, and it is load-bearing.**

`check_duplicate_output_names` was first placed at `name_binding.rs:190` and moved
to the END of the `Select` arm because `:190` made
`output_alias_later_does_not_exempt_earlier_bare_ref_nb001` red. Verify from the
code that NB-001 genuinely reports first for **every** shape where both would
fire, not merely for that one test. A query that should report NB-001 but now
reports NB-005 gives the user a misleading remedy — it tells them to rename an
output column when the real problem is that the input does not bind.

**A2 — is universal NB-005 actually right?** This is the highest-value question
here, and it is a judgement call the orchestrator made, not a fact.

`SELECT a.id, b.id FROM a JOIN b` is now a hard error in this engine and is legal
in every comparable one. Find a legitimate shape this newly rejects. Consider in
particular: ad-hoc/debug queries, the demo SQL under `demo/**`, `velo-test`
fixtures, anything in `docs/` not covered by the enforced-docs gate, and
`SELECT *`-adjacent forms. If the corpus gate passes but real user SQL would
break, say so — the gate covers 72 enforced files, and see A5 for why that number
should not be trusted on its own.

**A3 — the helper MOVE, not copy.** The naming helper moved from
`plan/schema_propagation.rs` into `ast.rs` so validation and planning share one
implementation. Confirm there is exactly ONE implementation now and that
`validation/` did not gain a dependency on `plan/` (the module doc states it is a
pure AST walk: no schema, no catalog, no plan). Confirm the planner's emitted
names still match what NB-005 polices — if they diverge, NB-005 rejects names the
planner never produces, or misses ones it does.

**A4 — the Class B aliasing did not weaken 8 tests.** Eight tests had colliding
items aliased (`a.id` → `a.id AS a_id`) with assertions unchanged, on the grounds
that aliasing changes output names but not which relation each item resolves to.
Verify that per test. If any of them was actually asserting something ABOUT the
collision, aliasing silently deleted its coverage. Pay attention to
`test_primary_key_marks_at_most_one_field_on_bare_name_collision`, whose name
contains "bare name collision", and to
`selected_system_columns_are_output_columns_over_a_join` (`a._OFFSET, _OFFSET`) —
system columns have per-row identity semantics in this repo.

**A5 — `medium1_same_name_no_alias_collision_build_wins` via `SELECT *`.**

It was re-expressed as `SELECT *` because aliasing would have deleted its subject
(which side wins a same-name merge). **Verify `SELECT *` genuinely reaches the same
merge path** and that the test still fails if build-side-wins were broken. If it
now passes vacuously, a real behaviour lost its only coverage — and NB-005 made it
untestable from SQL, which is a finding in itself.

**A6 — the doc edit.** `SELECT-ALIAS-REUSE.md:148`, one line, second alias renamed
to `amount_with_markup`. The block teaches alias *shadowing* — that `amount * 1.1`
reads the aliased value. Confirm the lesson survives and that no other block or
doc was touched.

**A7 — wildcard skipping.** `SelectField::Wildcard` is skipped entirely (expanding
`*` needs a schema this validator lacks; case 4 is #1931). Confirm a select list
containing a wildcard STILL has its non-wildcard items checked against each other,
and that the skip cannot be used to smuggle a duplicate past NB-005.
