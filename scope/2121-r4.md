## Why the rename happened — context you need

`parser/tokenizer.rs:392-395` starts an identifier on `is_alphabetic() || '_'` and
continues only while `is_alphanumeric() || '_'`. So `$` **terminates** an
identifier and `SELECT EXPR$0 FROM t2` cannot tokenize. The issue is titled
"duplicate output field names, **unreferenceable downstream**" — `EXPR$<n>` fixed
the duplicate half and left the referenceable half broken. `EXPR$<n>` is
Flink/ksqlDB's form, but their referenceability rests on quoted identifiers this
parser does not support.

**The rename increases collision surface, deliberately.** `EXPR$0` was
unconstructible via the parser; `EXPR_0` is. So `SELECT price * qty, some_col AS
EXPR_0` can now collide. #1918 adds NO collision handling — #1919 owns that — and
`user_column_named_like_a_generated_name_is_not_silently_merged` pins that the
collision is VISIBLE rather than silently merged. Confirm it is visible, and that
nothing in this delta silently dedups.

## Attack these

**A1 — the field-order fix (`1b7979745`, `columnar/adapter.rs`). Highest risk.**

`batch_to_records` built each record's fields into an `FxHashMap` and let hash
iteration decide the emitted column order — while the function's own doc promised
"the order of fields … matches the schema order". The order was stable only by
hash accident, and the rename shifted the hashes. The fix builds a `Vec` in schema
order.

This is a **columnar egress path**, so:
- Is schema order the correct order here, or is there a consumer that depended on
  the previous (accidental) order? Check `pack_join_results` / `from_rows` /
  anything comparing two batches field-by-field.
- Does the byte-parity contract (`group_by_columnar_parity_test`) still hold, and
  does it compare by name or by position?
- `from_explicit` is documented as the order-preserving constructor. Verify the
  fix actually reaches it and does not round-trip through a map again downstream.
- Per this repo's streaming-compliance rules, a field-order change on an egress
  path touches per-row identity. Confirm no system column (`_offset`, `_key`,
  `_event_time`, `_traceparent`) changed position or was dropped.

**A2 — the same class elsewhere.** The bug was "a map decides an order that a doc
promises is the schema's". Grep for other `FxHashMap`/`HashMap` field
accumulations on emit paths that a rename could have shifted, and say whether any
carry the same latent nondeterminism. The rename only exposed this one because it
perturbed hashes — others may be sitting there unexposed.

**A3 — did the 159-reference rename miss anything?** A missed literal is a test
asserting a name nothing produces, or a doc telling users the wrong name. Check
`src/`, `tests/`, `docs/sql/PARSER_GRAMMAR.md`, and any remaining `EXPR$`/`GROUP$`
in comments. Doc changes must be prose only — no edits inside ```sql fences.

**A4 — R16a, the headline test.** `generated_output_name_is_referenceable_by_a_downstream_query`
asserts `CREATE TABLE t2 AS SELECT price * qty FROM trades` then
`SELECT EXPR_0 FROM t2`. Does it genuinely resolve against the **registered**
schema, and assert the returned value — or does it stop at parsing? Only the
registered form persists for later queries, and this is the claim the whole issue
rests on.

**A5 — R14 in both stores.** The guard must still fire for the bare-column case
#1322/#1323 were written for, and must NOT over-fire: `symbol AS s` is a
legitimate second name for the same key value and must still be emitted.
Case-insensitivity makes over-firing easier, not harder.

**A6 — R15's execution test.** Does it assert the **filtered value**, or only that
a name exists? Round 3 found the previous version asserted nothing meaningful.
