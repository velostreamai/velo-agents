# Scope — PR #2154 (#2150), round 2

**Round 1 blocked this PR.** This round reviews the fixes, scoped to the delta since `e502ebf58`.

Round 1 produced findings from both gates, each catching what the other missed. The strongest: every `Arc::ptr_eq` assertion targeted probe *data* columns, so **loop 3 — the 7-column system tail, 7 of the 13 refcount-bumps the entire measured win rests on — had no regression guard at all.** Reverting it to `take` left all 6 tests green, because `take` under the identity permutation produces identical values. The suite verified the *values* and never the *sharing*.

## Attack these

**C1 — do the new guards actually guard?** G1 adds `ptr_eq` on `_offset` and `_headers`. Verify by construction that reverting loop 3 to `take` now fails, and that reverting loop 1 fails too. Then ask the harder question: is there a *third* mutation that both loops' guards miss? Specifically — could the fast path fire for the data columns but not the system tail (or vice versa) and still pass? They branch on the same flag today; if a future edit split that, would the suite notice?

**C2 — the sliced-batch test (G2): does it pin what it claims?** The author reported that under a `take` fallback *every per-row value assertion passed* and only `ptr_eq` failed, concluding that `ptr_eq` does the guard work. Assess that. The intended purpose was pinning offset-correctness of the CLONE path behaviourally rather than by citation to arrow internals. Does the test do that — i.e. would it fail if `Arc::clone` returned an array whose offset was mishandled? Or does it only prove the fast path fired? If the latter, the G2 objective is unmet and the arrow-version invariant is still uncovered.

**C3 — G1's index derivation.** Indices come from `index_of` on each side's own schema, because `out.batch` inserts build columns between probe data and the probe system tail. Verify that derivation is correct for both schemas and cannot silently resolve to a wrong column — and that `expect()` on a missing column is the right failure mode in a test.

**C4 — the retention doc (G4).** It records four claims: amplification is parent_rows/slice_rows on the *emitted* slice; retention is per parent batch not per joined record; `get_array_memory_size` sums `capacity()` so accounting over-charges rather than under-counts; and the exposure is confined to file/Parquet sources, not Kafka poll batches. **Each of these was contested or got wrong by at least one round-1 reviewer** — one gate computed <2× amplification by reasoning about the wrong slice. Verify all four against the code. If any is wrong the doc is actively misleading, which is worse than silence.

**C5 — G3's corrected comments.** Round 1 found that test 2 does not isolate the `row_match_count > 1` arm (probe row 1 also matches zero, so the `== 0` branch clears the flag independently) and that test 3 covers that arm only incidentally, via a `try_new` length mismatch rather than its own assertion. Confirm the rewritten comments now state what each test actually pins, and that no new overstatement was introduced while fixing the old one — that failure mode has already happened once on #2152, where a doc correction overshot in the opposite direction.
