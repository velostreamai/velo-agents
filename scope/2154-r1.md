**First review of this PR.** Authored by sonnet; the two gate findings in it were also sonnet's, from the orchestrator's `/check-code` pass. You are independent of both.

**Read this first.** On the sibling PR #2152, one gate returned *approve-with-findings* after doing real work — it cloned the worktree, ran a mutation, and found MORE failing tests than the author reported — and still missed a **P1 silent-wrong-output regression** that the other gate found by reading. Its consumer audit concluded "every consumer resolves by name"; the one consumer that resolved a column count by *subtraction* was never in the list it enumerated. The orchestrator's own `/check-code` pass missed it too, for the same reason: it checked the enumerated consumers instead of re-deriving who consumes the property that changed.

That is the defect shape of this entire issue family — **an enumeration that looked complete**. Assume it applies here.

## What it does

`take_combine_stream_table_with_left` materialised the joined batch with three `take`-kernel loops. When every probe row matches exactly one build row (the canonical N:1 enrichment join), the probe-side selection is the identity permutation and `take(col, [0..n))` is a bit-identical copy — so loops 1 (probe data) and 3 (probe system tail) now `Arc::clone` instead. Loop 2 (build side) is untouched.

Measured: take-kernel share **18.57% → 2.12%**; `take_combine_stream_table` inclusive **26.06% → 10.92%**. 13 of 16 takes become refcount bumps.

The whole safety argument is that **the detector is exhaustive**. If a non-identity selection is ever classified as identity, the output silently carries the wrong rows.

## Attack these

**A1 — is the detector exhaustive?** It tracks a per-row match count and clears on NULL probe key, zero matches, and `count > 1`. Enumerate every OTHER way `probe_idx_buf` can end up not equal to `[0..n)`, or every path that reaches the `take`/clone loops with the flag still true. Specifically check the **early-return paths** — empty build index, empty key-index list, `probe_idx_buf.is_empty()` — and whether any of them can leave the flag set while still producing output. Also: can `n_probe` ever differ from the length of the columns being cloned? The clone's correctness depends on `n_probe == probe_batch.num_rows()` for **every** column, data and system alike.

**A2 — sliced input batches: memory retention.** Probe batches can carry a non-zero offset (`datasource/file/reader.rs:2861` `batch.slice(want, …)`, `physical_operator/limit_operator.rs:245` `batch.slice(skip, take)`), so a probe column may be a slice of a much larger parent buffer. `take` compacts to a fresh offset-0 array of length n; `Arc::clone` retains the parent. Cloning a 32-row slice of an 8192-row batch therefore keeps all 8192 rows alive for as long as the joined record is held — and joined records are buffered downstream. Quantify whether this is a real retention regression in a streaming pipeline, and whether any batch-sizing or memory-pressure accounting (`MemoryPressure`, coordinator batch budgets) now under-counts because it measures logical rows rather than retained buffers.

**Already refuted — do not re-derive:** the related *correctness* worry that `.values()` would read the wrong window on a cloned sliced array. `PrimitiveArray::slice` slices the `values` `ScalarBuffer` itself (`arrow-array-58.4.0/src/array/primitive_array.rs:836`), so `.values()` is offset-correct and `i64_values_and_nulls` / `max_nullable_i64_arrays` read the right range. Confirm if cheap, but it is not the finding.

**A3 — the cached-schema interaction.** `joined_schema` may come from `cached_schema`, possibly built at an earlier schema generation (this is exactly what #2146's gate found twice). Under the fast path the output arrays' *identities* change but their count and order should not. Verify the fast path cannot make a stale-cache mismatch go from a loud `RecordBatch::try_new` error to something silent — the `try_new` error was the only runtime detector of a stale cache, and #2146 lost it once already.

**A4 — per-row system-column identity.** `_offset`, `_key`, `_headers` (Map-typed), `_traceparent`, `_event_time`, `_timestamp`, `_partition` carry per-row identity that DLQ routing (`RowErrors::row_index` → originating Kafka offset), trace propagation and watermark advancement depend on. The claim is that `Arc::clone` under a verified identity selection preserves alignment trivially. Test the claim at the boundary: what if the build side supplies `_event_time` (the `max_taken_with_build_side` `Some` branch) — verified by one new test — and what about a probe batch whose system tail is a different length from its data columns, if that is constructible.

**A5 — the debug_asserts.** Two cross-checks guard the detector, compiled out under `debug-assertions = false`. Confirm (a) they genuinely compile out on `[profile.profiling]` / `[profile.release]`, so the measurement is honest, and (b) they genuinely fire in test builds, so they are not decorative. A `debug_assert` that never runs anywhere is worse than none — it reads as a guard while guarding nothing.

**A6 — test discrimination, not test presence.** 6 tests. The decoy test (`identity_fast_path_len_equals_n_probe_decoy_is_not_identity`) is the important one: it pins that `probe_indices.len() == n_probe` is NOT a sufficient detector. The author reports verifying it discriminates by temporarily forcing the wrong detector. Judge whether each test would fail for the right reason — in particular whether the fast-path tests would still pass if the fast path silently stopped firing (`Arc::ptr_eq` assertions are what prevent that; check every test that needs one has one).

## Do not report

- **The design.** Cross-operator late materialisation was refuted by the #2148 spike (`StreamRecord.batch` is a public field; Arrow 58 has no selection-vector concept). The detector's placement inside the existing probe loop is pinned.
- Loop 2 (build-side takes) not being optimised — inherent to a hash join, deliberately out of scope.
- Filter/projection fusion into a single take — deliberately deferred, conditional on this PR's re-profile.
- Style, naming, comment density.
