## The one piece of genuinely new logic — attack this

R1's first fix paired lifted slots to consuming wrapper fields **greedily,
one-to-one**. That was wrong and is gone: `SELECT SUM(a) + SUM(b)` pushes TWO
slots (`walk_expr_for_aggs` recurses both `BinaryOp` sides — two accumulators are
CORRECT, since `SUM(a)+SUM(b) ≠ SUM(a+b)` with nulls) for ONE wrapper, so the
second slot leaked `"SUM(b)"`. Widening to many-to-one would have given both slots
the same `EXPR$0` — two identically-named schema fields, the original defect
relocated.

R6 replaced it: iterate `field_sources`, name each from `alias_keys`, emit no field
for a lifted slot. **Verify that rewrite, not the old pairing.**

1. **Count and order.** The arm previously emitted one field per `agg_exprs`
   entry; it now emits one per aggregate-consuming SELECT field. For every shape
   you can construct, does the field COUNT and ORDER still match what the runtime
   emits? A silent off-by-one here mis-binds every downstream index.
2. **Consumers of that shape.** `HAVING` resolution, `ColumnResolution` index
   assignment, two-stage CTAS schema registration, and the columnar byte-parity
   contract all read this schema. The brief told the worker to STOP and report if
   any of them depended on the old count; it did not report one. Confirm that
   silence was correct.
3. **The orphan-slot commit** (`9285e7f7d`) preserves a one-field-per-slot path
   for programmatically built `Aggregate` nodes whose `field_sources` do not cover
   the slots. Is that path reachable from the parser? If it is, there are now two
   schema shapes depending on how the node was built.
4. **`Computed` guard.** The new arm emits a field for a `Computed` field only
   when `expr_contains_aggregate_call` is true. A `Computed` field with NO
   aggregate (`SELECT price * 2 FROM t GROUP BY k`) therefore gets no field from
   this arm. Is that right, and was it right before?

## Shapes to construct and check

- `SELECT SUM(a), SUM(b) + SUM(c) FROM t GROUP BY k` — mixes the owned and lifted
  paths in one query. **The orchestrator verified by code read that R6 handles it,
  and confirmed NO TEST covers it.** If you agree it is correct, say so and it will
  be pinned by a test in a follow-up; if you find it broken, that is a P1.
- `SELECT CASE WHEN AVG(price) > 100 THEN 'x' ELSE 'y' END FROM t GROUP BY k` —
  `walk_expr_for_aggs` recurses into `when_clauses`/`else_clause`, so a lifted slot
  arrives from a CASE. One existing test uses this shape without GROUP BY.
- A lifted aggregate inside a non-aggregate `Function` arg (`ABS(SUM(a))`).
- `SELECT *, SUM(a) FROM t GROUP BY k` — wildcard consumes a position.

## Not a defect — do not "fix" it
`window_projection_operator.rs:207-216` computes `slot_lookup_name` from
`generate_field_name` while `output_name` comes from `alias_keys`. Round 1's
`code-review` called that a P1 write/read mismatch; `check-code` refuted it by
tracing `walk_expr_for_aggs → agg.alias → resolve_aggregate_key` and establishing
that the aggregate read key derives from the AST alias, never `alias_keys`.
`differential_test` asserting `EXPR$1`/`EXPR$2` across ten group-key shapes
corroborates. The real defect there is a per-row allocation; check whether the
worker moved it into the `Aggregate(_)` arm as briefed.
