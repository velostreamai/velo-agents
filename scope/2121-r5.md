## Attack these

**A1 — the `remove` is a correctness claim, not a perf tweak.**

`rows_window.rs` now DRAINS `result_fields` while building the ordered pairs. The
justification given was "`result_fields` has no reader after this point — HAVING at
~925, ORDER BY at ~965, alias lookups at ~829-868 all precede it". **Verify that
from the code, at the current line numbers.** If any path reads `result_fields`
after the drain — a later branch, a loop iteration, an early-`continue` that
re-enters — the second read now sees an emptied map and silently emits fewer
columns. That is a P1 and it would not redden a test that checks one row.

Also: the `debug_assert!` survives but the `None` arm is gone, so a desync now
DROPS a column in release instead of emitting a fabricated `Null`. Confirm dropping
is the intended failure mode and that nothing downstream indexes positionally in a
way a missing column would corrupt.

**A2 — `compact_record::to_stream_record` changed emitted order on an egress path.**

It previously emitted in `FxHashMap` iteration order; it now emits in
`self.schema` index order. The struct's doc says "values indexed by schema
position", so schema order is defensible — but this is a **behaviour change**.
Find its callers and say whether any compared two records field-by-field, or
consumed columns positionally, in a way the old accidental order satisfied.

**A3 — `project_into` generification: did any caller lose an inference it relied on?**

It went from a concrete `FxHashMap` parameter to `I: IntoIterator`. `show.rs`
needed an explicit annotation as a result. Are there other call sites whose
`collect()` or literal now infers differently, or that compile but build a
different container than intended? Check every `project_into` call site.

**A4 — the removed `forbidden` entry.**

`.agents/tasks/1918.json` had "Do not change the `EXPR$` prefix or the `$<n>`
form"; the orchestrator deleted it because the shipped code violates it after R16
renamed to `EXPR_<n>`. Deleting a rule one's own code breaks is a shape that
deserves scrutiny even when correct. Confirm: was R16's rename actually pinned by a
caller decision (it was — `$` terminates an identifier at
`parser/tokenizer.rs:392-395`, so `EXPR$0` was unreferenceable), and does the
edited spec now describe the shipped behaviour without also weakening an unrelated
constraint? These files govern every future dispatch, so an error here outlives the
PR.

**A5 — the new columnar test: does it reach the columnar store?**

`columnar_duplicate_group_name_guard_is_case_insensitive` is meant to drive
`ActiveState::drain_final` via `RuntimeContext::columnar_group_by` — the store the
existing R14 test does NOT reach. It deliberately omits
`force_legacy_group_by_for_tests()`. Verify it genuinely takes the columnar path
and not a fallback; if it silently runs the legacy store, the P2 it was written for
is still uncovered.

Note the orchestrator first placed this test **nested inside another function**,
where it silently was not a test at all, and caught it only because the run
reported `0 tests run`. Check the final placement is top-level and that it is
actually collected.
