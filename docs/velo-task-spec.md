## Problem

Coordinating detached work (gate legs, workers, review runs, CI waits) is not deterministic. In one session it produced wrong decisions and noise:

1. Completion is inferred from absence: `velo-watch` diffs `ps | grep` output and record-file line counts; `velo-orchestrd` treats "dead `<log>.pid` + a log exists" as finished. A crash, kill, timeout and success are indistinguishable; no exit code or cause is recorded.
2. Tasks have no identity: the watcher wakes on any change to any gate, worker or CI run.
3. Timeouts are not enforced by the coordinator (one global `--max`; each task's own SDK timeout decides).
4. Arming late misses the event: `velo-watch` prints "nothing running to watch" and exits 0 if the work finished first.
5. Detached launches (`nohup` + `*.pid` in `velo-pr-gate`) leave no recorded outcome; the harness reports the wrapper shell's exit, not the task's.
6. Ad hoc waiters: six near-identical `until pgrep -f …` loops were stacked on one condition.
7. The harness push notification is itself unreliable (see prior art), so nothing may depend on it.

## Operator model: the orchestration agent

`velo-task` is operated by the **orchestration agent** (an LLM session), not by a person typing commands. The design target is that agent's failure modes, observed in the originating session: ending a turn while detached work still runs; reading a wrapper's exit as the task's exit; forgetting to re-arm a watch after a restart; trusting a stale "done"; improvising `pgrep` loops. Consequences, all binding:

- One call, one verdict: `velo-task wait` prints one line per id, `<id> ok | failed(n) | timeout | killed | lost | upstream-failed(<parent>)`, and its exit code mirrors it (0 iff `ok`). The agent never interprets a log tail or a process list.
- The harness cannot end the turn while tasks run (R10) and a new session is told what is in flight with ready-to-run commands (R11). Nothing relies on the agent remembering to arm anything.
- Every non-`ok` or unknown state fails safe: it is surfaced loudly and never read as success.
- Nothing the agent must decide (is it alive? did it time out?) is left to inference: the launcher records it (R4, R12).

## Scope: the whole velo workflow

Every velo command that detaches or waits on work shares these failures, so this is a workflow-wide primitive, not a gate fix: `velo-pr-gate`, `velo-gate-run`, `velo-gate-post`/`-finish`, `velo-merge --wait`, `velo-orchestrd`, `velo-watch`, `velo-dispatch` (workers and `records/*.result.jsonl`), `velo-status`, `velo-local` runs, the retro/review scratch runners and any ad hoc session waiter. Live evidence from the originating session: `velo-watch` armed for the #2768 gate and printed `gates:` (empty), i.e. it was watching nothing while the gate ran. Phasing is by risk, not by in/out of scope; all phases are committed: P1 core + `velo-pr-gate`/`velo-gate-run`/`velo-watch` gate mode/`velo-orchestrd` gate completion; P2 `velo-dispatch` workers + `velo-status` + `velo-merge`; P3 retro/review runners and the session procedure.

## Decision: build `velo-task` on Vanth (spike 2026-10-27, owner-approved: "simplest, daemon is ok")

Three review lineages preceded this: a bespoke supervisor (16, 7, 4 P1s over three Codex rounds), then `velo-task` over pueue (4, 7, 6, 3, 2, 1 P1s over six rounds; every fix to the wrapper's own bookkeeping, labels, markers, launcher, queue handling, produced a new race). A fault-injection spike of pueue 4.0.4, spoolctl 0.4.11 and Vanth 1.14.0 (evidence: `~/.agents/state/scratch/spike-2769/results.md`, raw logs and test scripts beside it) showed the runner, not the wrapper, should own the verdicts:

| Need | Vanth 1.14.0 | spoolctl 0.4.11 | pueue 4.0.4 |
|---|---|---|---|
| Closed verdict set | all five natively (`completed`, `failed`+code, `timeout`, `cancelled`, `orphaned`) | four; `lost` only with `--max-crashes 0` | `ok`/`failed`/`killed` only |
| Deadline + tree kill | `--timeout`, tree gone in 3 s, TERM-ignoring child killed | yes | none (`gtimeout` wrapper) |
| Runner/daemon death | daemon death harmless; runner death → `orphaned` at once, no replay | job stays `running`; default **re-runs** it | orphan relabelled `Killed` |
| Dependencies | `--trigger`: failed parent → child `cancelled` with reason | none | yes |
| Durable dedup | `--idempotency-key`, also after completion | active jobs only | none |
| Names, tags, list | `--name`, `--tag`, `list --json` | key only | labels |
| Secrets | `--env` only, caller env **not** copied | argv/`--env` | **whole caller env stored and served** |
| Maturity | ~50 releases since 2026-08-18, one author, Apache-2.0 | 0.4.11, one author | 2015, 6.4k stars |

Accepted costs of Vanth (all in the requirements below): a localhost HTTP daemon (`127.0.0.1:48217`, bearer token, autostarted by any CLI call); `wait` exits 0 on any event, so the verdict is always read from `--json`; a killed shell with a surviving grandchild keeps the job `running` until `--timeout` fires; state files are 0644 inside a 0700 home; it cannot wake a Claude Code session (wake targets are Codex, OpenCode, a local command, a webhook), so the Stop guard is ours; it is weeks old and single-maintainer, so the package is **pinned and vendored by hash** (R12). `vanth setup` (which edits `~/.claude.json`, `~/.codex`, `~/.config/opencode`) is never run.

## Requirements

- R1. Closed verdict set, mapped from `vanth --json status <job_id>`. Vanth's terminal statuses are exactly `completed`, `failed`, `timeout`, `cancelled`, `orphaned`; its normal lifecycle writes are `queued`, `launching` and `running` (the CLI also advertises `paused`, `retrying` and `stopping`; all six form the single **in-flight predicate** `IN_FLIGHT = {queued, launching, running, paused, retrying, stopping}` used by every component, including the Stop guard). `velo-task` never passes `--policy` or any restart option to `vanth start`; a row whose `policy_state_json` is non-empty with a restart pending (`restart_after` set) is treated as in flight even if its status is `failed`/`orphaned`, so a policy relaunch can never be reported final. Mapping: `completed` → `ok`; `failed` → `failed(<exit_code>)` (a missing `exit_code` → `lost`); `timeout` → `timeout`; `orphaned` → `lost`; `cancelled` with `stop_actor=user` → `killed`; `cancelled` with `stop_actor=daemon` **and** the exact trigger-parent stop reason **and** a `trigger_json.$.job_id` that is a string matching `^[A-Za-z0-9_-]+$` **and** names a row present in `jobs.sqlite` or an entry of the local name index → `upstream-failed(<parent>)`; the exact reason string is the Vanth 1.14.0 literal `trigger parent reached an incompatible terminal status`, pinned and asserted by `install-vanth`; **every other `cancelled` (any other stop_actor: tool, watchdog, timeout, policy, remote, or an unrecognised reason) → `lost`**; an in-flight status → non-terminal; **any status outside both sets → `lost`** and counts as in flight for the Stop guard until acknowledged. The wrapper never infers a verdict from a log, a process list or `vanth wait`'s exit code.
- R2. **Every job is started with `--timeout S`**; `run` refuses to start without one (exit 2). The deadline is Vanth's (tree kill verified by the spike); the wrapper adds none of its own. A job whose shell was killed but whose grandchild lives stays `running` until `--timeout` fires (spike T7); that is the bound, and the Stop guard blocks until then.
- R3. **Identity comes from Vanth.** `job_id` is Vanth's durable unique id (no reuse); `--name <id>` carries the caller's id (`^[a-z0-9][a-z0-9_-]{2,63}$`: lowercase, digits, `_`, `-`; 3-64 chars, so the idempotency key below is always valid), `--tag velo`, `--tag issue:<N>` when `--issue N` (digits, ≤ 9), `--tag stage:<stage>` for pipeline stages. **`<id>` resolves from a local append-only name index, then is verified against Vanth, and every control path can also address a job directly by `job_id`:** `run` writes a durable *pending record* `<state>/pending/<nonce>` (id, idempotency key, the exact non-secret `vanth start` settings) **before** calling `vanth start`; after `vanth start` returns it appends the `job_id` as one line (a single `>>` write, so lines never tear) to `<state>/names/<id>` and deletes the pending record, and it **prints the `job_id`**. `wait|status|cancel|ack` accept either `<id>` (the last index line, then read with `vanth --json status <job_id>` and its `name` must equal `<id>` exactly, else exit 2) or `--job <job_id>`. This is complete for every job `run` started however many newer jobs exist (Vanth's `list` caps at 1,000 rows with no cursor, defaults to in-flight statuses, and `--name` is a substring match, so it cannot be the lookup). **Crash recovery reads Vanth's own acceptance record; it never replays blindly.** The pending record stores the *canonical structured* settings (command argv, resolved cwd, name, ordered tags, non-secret env map, timeout, trigger JSON, key), because Vanth's request-equality covers all of them. Vanth stores every accepted start in `local_start_requests` (key → request hash → `job_id`, committed in the same transaction as the `jobs` insert, replayable in every job state). `velo-task reconcile` (run by `status` and SessionStart) therefore reads that table read-only (`sqlite3 -readonly`): **if the pending record's key is present, the start was accepted** — append the recorded `job_id` to the name index and delete the pending record (no second execution is possible). **If the key is absent, the outcome is indeterminate** (the client may have died before sending, or the server before committing) and reconcile does **not** replay it: the record is reported `pending-unsent` by `status`, blocks the Stop guard (R8) like an unacknowledged `lost`, and leaves the decision to the orchestrator: `velo-task resume <pending-id>` replays `vanth start` with the identical settings (idempotent if it had in fact been accepted) or `velo-task discard <pending-id>` **tombstones** it by a single atomic `mv <state>/pending/<pending-id> <state>/pending/<pending-id>.discarded` (the complete record, settings and key included, is never removed before the tombstone exists, so a crash at any point leaves exactly one of the two names; the discard time is the file's mtime; the key stays reserved, so `--rerun` of that id uses a fresh nonce and a plain `run` of it is refused while the tombstone exists). Because a request that was sent may still commit after a snapshot saw the key absent, `reconcile` keeps checking `local_start_requests` for every tombstoned key, **with no time limit**: Vanth's request timeout is per socket I/O and the `start` handler keeps running after the client disconnects, so no wall-clock bound is safe. A handler cannot outlive its daemon process, so a tombstone is retired only (a) when its key is seen accepted (the job is surfaced as `lost(late-accepted)`, cancelled with `vanth stop`, and blocks the Stop guard until acknowledged), or (b) when the daemon has been restarted since the discard (the provenance start time, R11(d), is later than the tombstone's mtime) **and** a final check after that restart finds the key absent. Tombstones are tiny and do not block Stop while pending. This prevents a stale abandoned submission from being launched later alongside its replacement. Two concurrent `run`s (or `--rerun`s) of the **same id** are a caller error (ids embed the sha or a generation); a caller that uses the printed `job_id` is unaffected, and `<id>` then means the last appended job.
- R4. **Duplicate protection is Vanth's `--idempotency-key`** (charset `[A-Za-z0-9_-]`, 8-128 chars): `velo_<id>` for a plain `run` (a double submit returns the same job and runs once, also after completion); `--rerun` uses `velo_<id>_<epoch>_<pid>_<rand8>`. Because Vanth returns the *existing* job for a repeated key with identical settings, `--rerun` checks that the returned `job_id` is not already in the name index and, if it is, retries with a fresh nonce (up to 5, then exit 5); this guards a *sequential* rerun against silently reusing an old job (two colliding concurrent reruns return the same job to both callers, which is one execution reported twice, not a lost job). A key reused with different settings is surfaced as exit 5 (`IDEMPOTENCY_CONFLICT`), never ignored.
- R5. `wait <id…> [--any|--all] [--timeout S]` resolves each id (R3), polls `vanth --json status` (bounded, default 1 h) and prints verdict lines on stdout, diagnostics on stderr. `--all` (default) prints exactly one `<id> <verdict>` line per id once all are terminal and exits 0 iff all `ok`; `--any` returns when the first id is terminal and prints **one line, for that winning id only** (the others are named on stderr as still in flight); exit 2 unknown id; 3 bound hit; 6 daemon down. The exit code mirrors the verdict of the id(s) printed.
- R6. No decision depends on a push notification. `status` is cheap and always available. **Which operations may autostart the daemon is explicit:** only `velo-task ensure-daemon` (called first by `run`, `wait`, `status`, `ack`, `cancel`) starts it, and it does so under `env -i` with the allowlist and `umask 077` (R11); a bare `vanth --json status` (`"up": false`, which never autostarts) is the health probe. `velo-task` never calls a `vanth` subcommand that could autostart the daemon with the caller's environment.
- R7. **Daemon down.** If `ensure-daemon` cannot reach or start the daemon (any transport or startup error), `status`/`wait` exit 6 `daemon-down` and print the recovery command `velo-task restart-daemon`; no verdict is invented. Jobs keep running under their detached runners meanwhile (spike T6a, T14). **`restart-daemon`** is: read the pid from `daemon.json` and the provenance file (R11), verify they match, SIGTERM that pid only, wait for exit (bounded), then run the same `ensure-daemon` clean launch; it never calls `vanth restart` (which relaunches with the caller's environment). Running jobs survive it (their runners are detached).
- R8. **Stop guard.** A Claude Code `Stop` hook runs `velo-task status --running`, which reads Vanth's `jobs.sqlite` **read-only** (`sqlite3 -readonly`, explicit `.timeout 2000`; WAL mode lets it coexist with the daemon's writes; pinned schema; no daemon needed, so it also works with the daemon down). Its candidate query has **no age cutoff**: `SELECT job_id,name,status,exit_code,stop_actor,stop_reason,trigger_json,created_at,<end-time column> FROM jobs WHERE status NOT IN ('completed','failed','timeout','cancelled','orphaned') OR status='orphaned' OR (status='failed' AND exit_code IS NULL) OR (status='cancelled' AND stop_actor IS NOT 'user')` — a deliberate *superset* of the rows whose R1 verdict is non-terminal, unknown or `lost` (it excludes only clean `completed`/`timeout` rows, user cancels and `failed` rows with an exit code; every trigger-cancelled row stays a candidate so that a corrupt one — right actor and reason, missing or unrecognised `trigger_json.$.job_id` — is still judged) — and then applies the one `verdict_of` function to each (the SQL is only a pre-filter; `verdict_of` has the last word). For each candidate whose `verdict_of` is non-terminal-clean it records an incident (R15) if none exists. It prints the exact `velo-task wait --job <job_id>` / `velo-task ack --job <job_id>` / `resume` / `discard` command. There is no automatic release. **Blocking is defined by incident records (R15), not by ack files.** The hook blocks on (1) every row whose Vanth status is in flight (`queued`, `launching`, `running`) directly from `jobs.sqlite` — in-flight jobs are never incidents, so they need no lifecycle and an acknowledged `orphaned` row that later runs again blocks as in-flight again —, (2) every **open incident**, and (3) every `pending-unsent` record (R3); `ack` is the single atomic `mv` described in R15. **Fail closed:** if the state directory exists (so `velo-task` has started work) but the database cannot be read (locked past the 2 s timeout, schema mismatch, unreadable, or missing while the name index or any pending record exists) the hook BLOCKS and prints the failure and the one escape hatch, `velo-task stop-override --reason <text>`, which appends an audited line (time, reason, uid) to `<state>/overrides.log` and lets the current session end once; when the state directory does not exist at all the hook allows, since nothing was ever started. `install-vanth` asserts, with `PRAGMA table_info` for the pinned version, the `jobs` columns named here (`job_id`, `name`, `status`, `exit_code`, `stop_actor`, `stop_reason`, `trigger_json` — the trigger parent is `$.job_id` of that JSON, there is no separate column — `created_at`, and the end-time column) and the `local_start_requests` key and `job_id` columns.
- R15. **Incidents: one durable record per problem, one atomic acknowledgement.** Replaces separate ledger entries, ack files and fingerprints. (a) *Kinds:* `lost` (a job whose verdict is unknown or `lost`, including a `lost` job whose row has since vanished, displayed `lost(pruned)`) and `late-accepted` (R3). (b) *File:* `<state>/incidents/<job_id>.<kind>.<fp>` where `fp` is the first 16 hex chars of the SHA-256 of the row fingerprint (`none` for a row-less `late-accepted` incident); the name is **deterministic**, so two concurrent creators write the same name; written to a temp file, fsync, then published with `ln` (fails if the name exists; the temp is then removed), never `mv` over an existing name; contents are `kind`, the row fingerprint `status|exit_code|stop_actor|stop_reason|<end-time column>` (or `none`), and first-seen time; never edited afterwards. (c) *Open vs closed* is only the file name: no suffix = **open**; `.acked` = acknowledged; `.superseded` = closed because the job recovered. A transition is a single atomic `mv` of the same file, so a crash leaves exactly one of the two names. (d) *Creation:* every observation (`status`, `wait`, Stop hook, SessionStart, `reconcile`) of a blocking condition looks for the deterministic name in all three forms (open, `.acked`, `.superseded`); if any exists nothing is created (so an acknowledged `lost` row that is still in `jobs.sqlite` does not reopen, and two concurrent observers produce one record because `ln` of the same name succeeds once), otherwise the incident is published as above. Closing is by `mv` to the `.acked`/`.superseded` name, and `ln` is attempted only after the three-form check, so a close racing a create can at worst re-publish an open record for a condition that was acknowledged a moment earlier; the next `ack` closes it, and the stale duplicate has the same name as the closed one only if the closed form is absent at the moment of `ln`. A job observed running creates none (cleanup deletes only terminal rows). (e) *Blocking:* the Stop guard blocks on **every open incident**, whatever the job's current row says, and on `pending-unsent` records. (f) *Supersede:* an open `lost` incident becomes `.superseded` only when its job is observed with a clean-terminal verdict (`ok`, `failed(n)`, `timeout`, `killed`, `upstream-failed`); an absent row never supersedes it; a `late-accepted` incident is never superseded, only acked. (g) *Ack (compare-and-set):* `velo-task ack --job <job_id>`, under the per-job lock (R17), renames to `.acked` every open incident of that job whose stored fingerprint equals the **current** row's fingerprint, every open `lost` incident of a job whose row is absent, and every open `late-accepted` incident; an open incident whose fingerprint differs from a still-present row is left open, listed as `stale-ack-refused`, and the command exits 2; `ack --incident <name>` renames one; `ack --all-lost` renames every open incident of jobs that are not in flight and prints the list; an in-flight job is refused (exit 2). (h) *gc:* `velo-task gc` deletes closed incidents only for a `job_id` that is no longer in `jobs.sqlite`; closed incidents of a job still present are kept so (d) keeps suppressing duplicates. (i) *Cleanup paths:* Vanth deletes terminal rows several ways while leaving `local_start_requests`: CLI `vanth prune`, MCP `job_cleanup`, authenticated `POST /cleanup`, automatic retention (`VANTH_RETENTION_SECONDS`, `_INTERVAL_SECONDS`, `_DRY_RUN`; default off), and `vanth restore --yes`. So `ensure-daemon` launches with `VANTH_RETENTION_SECONDS=0` set explicitly, covered by the digest in the provenance file (R11(d)), and refuses a running daemon not launched that way; `velo-task` never calls prune, restore or `/cleanup`; `install-vanth` never registers Vanth as an MCP server; the hook (R10) denies the command forms `vanth prune` and `vanth restore` — a **guardrail against the orchestrating LLM's own mistakes, not isolation**: a job runs as the same uid and can reach `jobs.sqlite`, the bearer token and an absolute `vanth`, so a deliberately hostile job can delete rows; untrusted jobs are out of scope. Residual risk, stated: a row deleted or replaced out of band that no `velo-task` call ever observed cannot be detected, and a restore that reintroduces a row identical to an acknowledged one is indistinguishable from it.
- R9. **Resume.** The SessionStart hook lists running and unacknowledged-terminal jobs with their `wait` commands, from Vanth, not from GitHub.
- R10. Hand-written `until/while pgrep` wait loops are denied by a hook beside `require-wait.sh` (best effort).
- R11. **Secrets and state.** Vanth's runner hands each job its inherited environment, overlaid with explicit `--env K=V` values, and stores `--env` values in `jobs.sqlite`, returns them from `--json status` and puts them in argv; `--secret-env` only masks log output. So: (a) **no secret ever goes through `--env`, `--secret-env` or argv**; `--env` carries only non-secret values; (b) secrets reach jobs through the **daemon's own environment**: `ensure-daemon` starts `vanthd` directly (never via a Vanth autostart path) as `env -i PATH=… HOME=… VANTH_HOME=… AGENT_BG_HOME=… VANTH_DAEMON_PORT=… <keys in .agents/vanth.env.allow>`, the Vanth variables being `velo-task`'s own constants (overridable only by `VELO_TASK_HOME`/`VELO_TASK_PORT` for the test harness), so jobs see exactly the allowlisted variables and nothing else (single trusted user; any job can read an allowlisted key, which is the stated boundary; allowlisted secrets are visible in the daemon's process environment to the same user only; a value is never in any argv, which `ps` shows to every user: `velo-task` hands the values to the helper that holds the lock and to the helper that starts the daemon on a descriptor (`--secrets-fd`), and they enter an environment only there); (c) the daemon is started under `umask 077`, so `jobs.sqlite`, `logs/`, `events/` and `daemon.json` are created 0600 (Vanth itself only enforces 0700 on the home and 0600 on its token); (d) **provenance**: when `ensure-daemon` starts the daemon it writes `<state>/daemon.provenance` (pid, the process start time rendered by `LC_ALL=C TZ=UTC ps -o lstart= -p <pid>`, and a digest of the launch command, which holds the names, never the values, of the allowlisted variables the launching environment sets: a call from an environment that would launch the daemon differently does not adopt it), and every call re-renders the live process's start time the same way (`LC_ALL=C TZ=UTC`, so the locale of the caller never matters), checks the pid is alive and equals `daemon.json`'s pid, and that `daemon.json`'s `started_at` is within 5 s of the provenance start; a stale provenance (reboot, pid reuse) therefore fails the start-time comparison; provenance is **identity, not an attestation of environment or umask**: it proves only that this daemon is the one `velo-task` launched. A daemon without valid provenance (including one started any other way) is never adopted: `ensure-daemon` refuses it with exit 6 and the instruction `velo-task restart-daemon`, and every `ensure-daemon` also verifies the current modes (0700 home, 0600 `jobs.sqlite`, `daemon.json`, token) and refuses on a looser mode. The allowlist file is a **fixed, validated set of secret names**: each key must match `^[A-Z][A-Z0-9_]*$` and is rejected if it equals or starts with `PATH`, `HOME`, `IFS`, `ENV`, `BASH_ENV`, `SHELLOPTS`, `PYTHON`, `DYLD_`, `LD_`, `VANTH_`, `VELO_TASK_`, `AGENT_BG_` or `TMPDIR`; the interpreter, `vanthd`, `env`, `ps` and `sqlite3` are invoked by absolute path from the pinned install.
- R12. **Supply chain.** Vanth runs from a dedicated venv built by `velo-task install-vanth` with the pinned interpreter (CPython 3.12, wheels only: `--only-binary :all:`, PyPI index only) from `requirements/vanth.lock`, a fully resolved requirements file with a hash for **every** distribution in the installed tree (about 30, including the platform wheels for `cryptography`, `cffi`, `pydantic-core`, `rpds-py`), installed with `--require-hashes`; upgrades are a reviewed change to the lock. `vanth setup` is never run and the bundled `vanth-monitor` binary is never executed. The daemon binds 127.0.0.1 only (a bar asserts it).
- R13. **GitHub is a ledger, never control flow** (section below).
- R14. Pipeline stages are chained with Vanth `--trigger` (section below).

## Design: `velo-task`, a thin bash 3.2 wrapper over `vanth` (a thin bash 3.2 front end plus a small tested stdlib-Python helper `velo-task-state`, R17)

- `velo-task run <id> --timeout S [--issue N] [--stage ST] [--after <id>:<status>…] [--rerun] -- cmd…` → `vanth --json start --name <id> --timeout S --idempotency-key <key> --tag velo [--tag issue:N] [--trigger …] --env … -- cmd…`; prints the `job_id`.
- `velo-task wait`, `status [--running] [--issue N] [--json]`, `ack`, `cancel <id>` (`vanth stop --signal terminate --kill-after 5`; verdict `killed` once Vanth reports `cancelled`), `project`, `install-vanth`.
- Total mapping function `verdict_of(status_json)` is the only place a verdict is computed (one tested function).

## GitHub projection (issues, assignment)

GitHub is the durable human-visible ledger, never the control plane. Projection runs in `velo-task project` (also called by the Stop and SessionStart hooks), never inside the verdict paths of `run`/`wait`/`status`, each `gh` call under `timeout 10`. For jobs tagged `issue:N`:
- Assignment stays with `velo-dispatch`; `velo-task` never changes assignees.
- On a terminal verdict, one comment per `job_id` carrying the marker `<!-- velo-task:<job_id> -->` and the verdict line, created only after a paginated search for that marker finds none. `job_id` is unique forever, so a marker can never collide with a later run.
- Label `task:attention` is derived, not toggled: set iff any local job for that issue is `failed|timeout|lost|killed` and unacknowledged, removed otherwise.
- A failed `gh` call leaves the job pending projection (`proj-pending` on stderr) and never changes a verdict.

## Pipeline: the whole workflow as chained tasks

Stage names are `<issue>-<stage>`, chained with Vanth `--trigger '{"job_id":<prev>,"status":"completed"}'` (`velo-task run … --after <id>:completed` resolves `<id>` to its `job_id`); a failed parent makes the child `cancelled` with a stated reason, read as `upstream-failed(<parent>)` (R1); each stage's verdict gates the next. Every stage is submitted with an explicit `--timeout`.
1. `dispatch`: `velo-dispatch` validates the ticket, prepares the worktree, assigns the issue.
2. `drift`: **blocking** spec/drift check: the brief's anchors (symbols, ast-grep patterns, test names) resolve against the worktree base; failure ends the pipeline before any work.
3. `index`: `zg index` for the worktree; ok iff `zg status` reports fresh.
4. `work`: the worker; its domain outcome (`landed`/`stopped`) stays in `records/*.result.jsonl`, and a job terminal state bridges to a records line when the worker wrote none (a dead worker is never silent).
5. `gate`: `velo-pr-gate` legs, each a job named `gate-<pr>-<leg>-<sha9>`.

`velo-task status --issue N` shows the whole pipeline.

**Gate sizing** (computed from the diff by `velo-pr-gate`; tiers are evaluated T0 first, then T3, then T1, else T2, so a six-file docs-only diff is T0; "hot-path" and "streaming-compliance" are the path lists in `rules/gate-paths.txt` (the files named under the policy's streaming-compliance section plus `src/velostream/sql/execution/{processors,window_v2,algorithms}/**`), one list shared with the policy; the tier and the legs it implies are printed in the plan, and a planned leg that does not run is never a pass, only an owner waiver):
- T0 docs / `.agents/` tooling only: no legs, CI only.
- T1 ≤3 files, no `src/` hot-path or streaming-compliance files: check-code (free), plus check-spec if the PR closes an issue with bars.
- T2 `src/` change, not T3: T1 plus Codex code-review.
- T3 hot-path or streaming-compliance files, or >300 lines or >5 files: T2 plus second-opinion and a perf check; an oversized PR is chunked, not gated whole.

## Integration

- `velo-pr-gate` owns the leg launches (`nohup` + pid files): move them to `velo-task run` with ids `gate-<pr>-<leg>-<sha9>`; default deadlines (env-overridable): codex review 45 min, free check-code 20 min, velo-local legs 60 min. A leg that is not `ok` is never posted as a report.
- `velo-gate-run` calls `velo-pr-gate --exec --wait`: wait via `velo-task wait`; replace the `review.log.pid` removal with a rerun and the second-opinion grace kill with `velo-task cancel`.
- `velo-orchestrd`: replace "dead `<log>.pid` + log present ⇒ finished" with the task outcome; parse a verdict only from an `ok` leg; any other outcome raises an attention event.
- `velo-watch`: only its gate mode moves to `velo-task wait`; `--attention` and worker-record modes are unchanged in v1. The CI poll becomes a task that exits 0 only when all required checks passed.
- Workers (`velo-dispatch`, `records/<issue>.result.jsonl`) are phase P2 (committed): the worker process becomes a task; its domain outcome (`landed`/`stopped`, commit data) stays in the records stream and a job terminal state bridges to a records line when the worker did not write one (crash/timeout), so a dead worker is never silent. `velo-status` and `velo-merge --wait` read task outcomes.
- Session procedure (CLAUDE.md): one `velo-task wait` per batch, `run_in_background: true`; on any doubt run `velo-task status`.
- Stop hook and SessionStart listing (R10, R11), registered beside `require-wait.sh`.
- Hook beside `require-wait.sh`: denies the obvious `until/while pgrep -f` loops (text heuristic; indirect forms evade it, as with `require-wait.sh`).

## Acceptance bars (macOS, `/bin/bash` 3.2, `tests/run.sh`; an isolated `VANTH_HOME` and port; each names its mutant)

- B1. exit 0 → `ok`; exit 42 → `failed(42)`. *Mutant: always `ok`.*
- B2. A job outliving `--timeout` → `timeout` and a spawned grandchild that ignores TERM (asserted by its own pid) is gone within timeout + grace + 2 s. *Mutants: drop `--timeout`; kill only the immediate child.*
- B3. `run` without `--timeout` exits 2 and starts nothing. *Mutant: default timeout.*
- B4. `wait` armed after completion returns at once; a failed job exits non-zero even though `vanth wait` exits 0. *Mutant: use `vanth wait`'s exit code.*
- B5. `wait --any A B` prints one line, for the first id to become terminal, in both orderings (A first, then B first); exit 0 iff that id is `ok`; the other id is named on stderr. `--all` prints one line per id. *Mutants: exit 0; print a line for the unfinished id.*
- B6. `wait --timeout` exits 3 naming running ids; an unknown id exits 2 at once. *Mutants: exit 0; treat unknown as running.*
- B7. Two concurrent waits on one id both return; `wait A` ignores B. *Mutant: return on any change.*
- B8. **Runner death**: `kill -9` of the job runner → `lost` (never `ok`, never `killed`), no replay (`runs=1`). *Mutant: map `orphaned` to `killed`.*
- B9. **Daemon death and restart**: `kill -9` of `vanthd` with a job running → the job still completes and its verdict is read after `ensure-daemon` restarts the daemon; with the daemon unstartable (test seam: `VELO_TASK_VANTH_BIN` pointing at a stub that fails to start) `status` exits 6 and prints `velo-task restart-daemon` within 5 s; `restart-daemon` run from a shell containing `OPENROUTER_API_KEY` leaves the new daemon's environment free of it and the running job alive. *Mutants: invent a verdict; hang; `restart-daemon` delegates to `vanth restart`.*
- B10. **Dedup**: a double `run` of one id starts one job (same `job_id`, `runs=1`; the key `velo_<id>` is accepted by Vanth, which the test asserts by reading the job back); the same key with different settings exits 5; `--rerun` creates a second job, and with the nonce generator stubbed to a constant the second `--rerun` detects that Vanth returned the existing job and retries (then exits 5 after 5 attempts). *Mutants: no idempotency key; ignore the conflict; a key containing `:`; no collision check.*
- B11. Ids `../x`, `a.b`, `a:b`, shorter than 3 or longer than 64 characters, or with a bad charset, and an `--issue` over 9 digits or non-digits are refused. *Mutant: drop the checks.*
- B12. `bin/velo-*` contain no `nohup` leg launch (grep-count over that fixed glob); a leg not `ok` is not posted (extends `test_gate_no_silent_skip.sh`). *Mutants: reintroduce one `nohup`; post regardless.*
- B13. The pgrep-loop hook denies a literal loop and allows `velo-task wait`; evasions asserted as known false negatives. *Mutant: allow all.*
- B14. Every script matching `bin/velo-task*` (fixed glob, fixtures excluded) runs under `/bin/bash` 3.2.x and is swept for bash-4 constructs; a seeded `declare -A` fixture must fail both. *Mutant: skip the fixture.*
- B15. `wait --all` prints exactly one `<id> <verdict>` line per id on stdout and `--any` exactly one line total; diagnostics go to stderr; exit mirrors the verdict. *Mutant: log tail on stdout.*
- B16. **Stop guard**: the read-only path (with the daemon killed) blocks for rows in `queued`, `launching`, `running`, `paused`, `retrying`, `stopping` (each, driven from the single `IN_FLIGHT` predicate), a `failed` row with a restart pending in `policy_state_json`, an injected unknown status (`mystery`), an unacknowledged `orphaned`, a `failed` row with a NULL `exit_code`, and a `cancelled` row with an unrecognised `stop_actor` — **each also when the row was created 400 days ago** — and for a `pending-unsent` record; does not block for clean `failed(7)`, `timeout`, `killed`, `upstream-failed`, `completed`; allows after `ack`; **refuses `ack --job` for a running job (exit 2) and ignores an ack once the row's fingerprint changes** (an acked `orphaned` row later set to `running` blocks again); blocks (fail closed, with the `stop-override` escape hatch) when the database is unreadable, locked past 2 s or has the wrong schema, and allows only when no state directory exists. *Mutants: `NOT IN` the terminal set only (hides `orphaned`); an age cutoff; omit `launching`; always allow; release after N blocks; ack with no precondition; ack with no fingerprint.*
- B17. **Projection never decides**: with `gh` stubbed to fail or hang (> 10 s), every verdict is unchanged and returned within baseline + 1 s; a terminal comment is created once per `job_id` and a crash between create and bookkeeping does not duplicate it (marker search); two concurrent `project` runs produce at most a duplicated ledger comment and never a different verdict or label. *Mutants: propagate the `gh` error; call `gh` inside `wait`; skip the marker search.*
- B18. **Fail-safe mapping**: injected statuses `orphaned`, an unknown string, a missing `exit_code` on `failed`, and a malformed JSON each map to `lost` (or exit 6 for unreadable JSON), never `ok`. *Mutant: default branch `ok`.*
- B19. **Pipeline**: with `--after A:completed`, a failed A makes B `upstream-failed(A)`, B's command never runs, and `status --issue N` shows the chain. *Mutant: run B anyway.*
- B20. **Gate sizing**: fixture diffs for T0..T3 yield the stated legs in the plan; a planned leg that does not run blocks `velo-gate --pass`. *Mutant: a fixed leg set.*
- B21. **Secrets**: with `OPENROUTER_API_KEY` and `UNLISTED_SECRET` set in the caller and only the former allowlisted in `.agents/vanth.env.allow`, a helper job compares its own `OPENROUTER_API_KEY` to the expected value and emits only a boolean (so the value never enters the log), and a second helper emits the *names* of its variables: the allowlisted key is delivered with its correct value (positive assertion), no other caller variable is present, and neither secret value appears in `jobs.sqlite`, `vanth --json status`, argv (`ps`) or logs. *Mutants: inherit the caller environment; pass the key with `--env`; drop the allowlist entirely.*
- B22. **State privacy and provenance**: with the daemon started by `velo-task`, `VANTH_HOME` is 0700 and `jobs.sqlite`, `logs/*`, `events/*`, `daemon.json` are 0600, and the fixture's `VANTH_HOME`/port are honoured (`env -i` preserves them); a daemon pre-started under `umask 022`, with the caller's environment, or even under `umask 077` with inherited secrets (provenance mismatch) is refused (exit 6, `restart-daemon` hint); a valid clean daemon is **accepted under a different `LC_TIME`/`LANG`** and across a fresh shell session; a provenance file left from a previous boot (live pid reused by another process, different start time) is rejected. *Mutants: drop `umask 077`; drop `VANTH_HOME` from the clean launch; skip the provenance check; compare locale-rendered `lstart`.*
- B23. **Supply chain**: `install-vanth` installs only from the lock with `--require-hashes`; the set of installed distributions equals the set in the lock (`pip freeze` vs lock, no extras, no missing); a tampered hash or a different version fails; `vanth setup` is absent from every script (grep-count 0); the daemon listens on 127.0.0.1 only (`lsof`). *Mutants: unpinned install; a lock missing one transitive dependency; bind 0.0.0.0.*
- B25. **Exact id resolution and recovery**: with 1,100 newer jobs whose names contain `gate-1` plus one older completed `gate-1`, `wait gate-1` resolves the older job through the name index and reports its own verdict; `gate-12` is never returned for `gate-1`; `wait --job <job_id>` works without the index; no match exits 2. **Recovery**: a `run` killed after `vanth start` returned (key present in `local_start_requests`) is recovered by `reconcile` after the job completed and after 1,100 newer jobs exist (`runs=1`, no second start); a `run` killed *before* `vanth start` (key absent) is reported `pending-unsent`, is **not** started by `reconcile` or SessionStart (verified by the absence of any new job), blocks Stop, and `resume` starts it exactly once while `discard` removes it. *Mutants: resolve via `vanth list`; substring match; skip the post-resolution name check; reconcile replays pending records automatically; reconcile searches `list` instead of reading `local_start_requests`.*
- B27. **Corrupt trigger cancel**: a `cancelled` row with `stop_actor='daemon'` and the exact trigger reason but a missing, malformed or unrecognised `trigger_json.$.job_id` is a Stop-guard candidate, reads `lost`, and blocks until `ack`. *Mutant: filter trigger-cancelled rows in SQL.*
- B28. **Late acceptance and discard**: with the request held server-side (test seam: the stub `vanth start` commits after a delay **longer than any watch window, e.g. 20 minutes simulated by a clock stub**), `reconcile` sees the key absent and reports `pending-unsent`; after `discard` and a `--rerun` replacement the delayed commit makes the original surface as `lost(late-accepted)`, get cancelled, and block Stop until acknowledged; the tombstoned key cannot be reused by a plain `run`; the tombstone is not retired by elapsed time alone but only after a daemon restart plus an absent-key check; `discard` is crash-atomic (kill between steps leaves exactly one of `pending/<n>` or `pending/<n>.discarded`, never neither). *Mutants: `discard` deletes then writes; a time-based retirement; no late-acceptance check.*
- B29. **Cleanup paths**: after `vanth prune --older-than 0 --yes` run directly, an unacknowledged `orphaned` job that `velo-task` had observed still blocks Stop as `lost(pruned)` until `ack`; the hook denies `vanth prune` and `vanth restore`; a daemon started with `VANTH_RETENTION_SECONDS>0` is refused (provenance digest mismatch) and the clean launch sets it to 0; **a job that was `running`, completed `ok`, then was pruned does not block Stop** (no incident for running; a superseded incident for clean-terminal); a recovered `job_id` that was pruned is `lost(pruned)`. *Mutants: no incident record; incident for running jobs (stale block); block only on rows present in `jobs`; retention left to the default.*
- B26. **Cancelled forms**: `cancelled` by user → `killed`; by trigger parent → `upstream-failed(<parent>)`; any other stop_actor (injected) → `lost`. *Mutant: map every `cancelled` to `killed`.*
- B24. **Resume**: SessionStart output lists a running job and an unacknowledged `lost` job with copy-pasteable commands. *Mutant: list nothing.*

## Prior art (what the rest of the field does, and fails at)

- Claude Code: a foreground timeout moves the command to the background; completion is pushed as a notification. [Notifications are silently lost](https://github.com/anthropics/claude-code/issues/89505); downstream, [an unbounded background-task wait hangs the turn](https://github.com/open-gsd/gsd-pi/issues/2904). → R5, R6.
- OpenAI Codex: [timeout kills the wrapper but orphans children (Linux/WSL report)](https://github.com/openai/codex/issues/4337); [background tasks cannot be killed](https://github.com/openai/codex/issues/8656); [task marked complete while background work continues](https://github.com/openai/codex/issues/52382); [a plugin task hangs with no timeout](https://github.com/openai/codex-plugin-cc/issues/49). → R2.
- OpenHands: [cancelling does not stop the process](https://github.com/OpenHands/software-agent-sdk/issues/5257); [background commands falsely time out](https://github.com/OpenHands/OpenHands/pull/8093).
- Devin CLI: [background shells tray, capped at 16](https://docs.devin.ai/cli/changelog/stable); nothing public on timeouts.
- Pi: [no built-in background bash or hidden sub-agents; use tmux](https://urandom.io/blog/2026-03-07-pi-dev-deep-dive).
- Task runners: [pueue](https://github.com/Nukesor/pueue) (spiked, not chosen: no deadline, leaks the caller environment, no dedup); [nq](https://sources.debian.org/src/nq/1.0-0.2/README.md) (flock-per-job, serial); [process-compose](https://www.linuxlinks.com/process-compose-process-manager-scheduler-orchestrator/) (declarative); GNU parallel [`--joblog`/`--timeout`](https://git.data.coop/tange/parallel/commit/f08db40a33f21b7c92e59687d624e0486f8bc951) (foreground).
- Orchestration frameworks, a different layer: LangGraph [run statuses](https://reference.langchain.com/python/langgraph-sdk/schema/RunStatus) and [durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution); [Restate](https://docs.restate.dev/foundations/key-concepts); [Hatchet](https://hatchet.run/versus/hatchet-vs-temporal).
- Deadline semantics: systemd `RuntimeMaxSec` / Kubernetes Job [`activeDeadlineSeconds`](https://plural.sh/blog/kubernetes-jobs) (a deadline fails, it does not retry); Temporal [heartbeat timeout](https://docs.temporal.io/concepts/what-is-a-heartbeat-timeout).

Source quality: the agent-framework items are issue trackers and community write-ups, not vendor docs; third-party limit figures disagree and are not relied on.

- B30. **Ack of any incident**: an observed `orphaned` job that is pruned still blocks Stop (open `lost` incident, shown `lost(pruned)`); `ack --job` renames it and Stop releases; a `late-accepted` job that was cancelled (row now clean `killed`) still blocks until acked; `ack --all-lost` over 30 mixed incidents (row-lost, pruned, late-accepted) plus one running job acks the 30, lists them, leaves the running job untouched and still blocking Stop as in-flight; a job with a `lost` and a `late-accepted` incident open at once is released only when both are acked (`ack --job` acks both). *Mutants: ack needs a current row; late-accepted superseded on clean-terminal; `--all-lost` acks a running job; second incident overwrites the first.*
- R16. **Late-acceptance ordering.** On seeing a tombstoned key accepted, `reconcile` performs, in this order: (1) create the `late-accepted` incident (R15(b), durable); (2) `vanth stop` the job; (3) retire the tombstone. Each step is idempotent and re-run from whatever state is found (tombstone present + no incident -> from 1; incident present + row in flight -> from 2; incident present + tombstone present -> 3), so a crash between any two steps loses nothing. Acknowledgement is one `mv` (R15(c)), so it has no intermediate state to recover.
- B31. **Crash points**: kill `reconcile` after each of the three steps in R16 and re-run: the end state always has an open `late-accepted` incident; kill `ack` before and after the `mv`: the incident is exactly open or exactly acked, never neither; an acknowledged `lost` row still present in `jobs.sqlite` does not reopen on the next `status`; after `gc` removes the closed incident for a vanished job, a restored differing row creates a fresh open incident. *Mutants: tombstone retired before the incident exists; ack writes a separate file then removes the incident; duplicate suppression ignores closed incidents.*
- B32. **Stop guard keeps in-flight blocking**: a `running` job with no incident blocks Stop; an acknowledged `orphaned` row that Vanth later retries to `running` blocks as in-flight; two concurrent `status` calls on one orphaned job leave exactly one open incident. *Mutants: Stop blocks only on incidents; random incident names.*
- R17. **Durable state is one small tested helper, with locks and fsync ordering.** Bash 3.2 has no fsync, SHA-256, JSON or locks, so all durable bookkeeping (pending records, tombstones, name index, incidents, provenance, locks, SHA-256, canonical JSON, the 2 s SQLite reads) is done by `velo-task-state`, a stdlib-only Python 3.12 helper run from the pinned Vanth venv by absolute path; the bash front end only parses arguments and calls it. `run` ordering, each step idempotent and re-done by `reconcile`: (1) publish `pending/<n>` (temp, fsync file, `mv`, fsync directory); (2) `vanth start` with the idempotency key; (3) append `job_id` to the name index (`O_APPEND`, fsync file, fsync directory if created); (4) unlink `pending/<n>` and fsync the directory. `reconcile` maps pending-with-accepted-key-but-no-index-line to step 3, so a crash after any step loses nothing. **Locks:** the helper takes an exclusive lock per `job_id` (`<state>/lock/job-<job_id>`) for every incident create, ack, supersede and gc, and a per-home lock (`<state>/lock/daemon`) for `ensure-daemon`/`restart-daemon`; locks are `flock`-style on a held file descriptor, released by process death. Every close transition is no-clobber (`link` new name then `unlink` old, failing if the destination exists). Creation re-checks the three forms **under the job lock**, so a stale creator cannot recreate an incident that was acked or collected.
- R18. **Daemon lifecycle.** Under the daemon lock `ensure-daemon` re-probes after acquiring it (another caller may have started the daemon); `restart-daemon` re-validates pid **and** process start time immediately before signalling, so a reused pid is never signalled. A body that has waited for a daemon to start or stop asks again whether it still holds the lock (its lock helper alive) right before it writes or retires a record or signals a process, so a body whose lock was lost meanwhile touches nothing of the new holder's. Concurrent `run` calls therefore start at most one daemon.
- R19. **Tombstones use daemon incarnations, not clocks.** Every daemon launch writes a fresh random `incarnation` UUID into `daemon.provenance`; `discard` records the then-current incarnation inside the tombstone. A tombstone is retired only when (a) its key is seen accepted (late acceptance, R16), or (b) the current incarnation differs from the tombstone's **and** a check of `local_start_requests` after that restart finds the key absent. If `vanth stop` fails or its acknowledgement is lost in R16 step 2, the incident stays open, the tombstone stays, the error is printed and `reconcile` retries on the next call; no step is skipped.
- R20. **Ordering and aggregates, decided.** `wait --any` returns the job with the earliest durable end time (Vanth's end-time column), ties broken by command-line order. `wait --all` and `wait --any` exit 0 only if every returned verdict is `ok`; otherwise exit 1, with every verdict printed one per line as `<id> <verdict>`; `lost` additionally exits 4 if any job is `lost`. A `status --job` for an id Vanth does not know and the name index does not list prints `unknown-job` and exits 3 and creates no incident; for an id the name index lists whose row is absent it reports `lost(pruned)` (incident per R15). `gc` deletes a job's closed incidents **and** its name-index lines together, under the job lock, only when its row is absent, so a collected job reads as `unknown-job`, never as a recreated incident.
- R21. **Deterministic test seams.** Crash and race bars use named failpoints and barriers, e.g. `pending.published`, `start.returned`, `index.appended`, `pending.unlinked`, `incident.linked`, `incident.closed`, `tombstone.retired`, `daemon.lock.held`: the helper reads `VELO_TASK_FAILPOINT=<name>[:exit|:wait=<barrier-file>]` only when `VELO_TASK_TEST=1` **and** the test capability holds: the nearest `.velo-task-test-root` marker file in a directory above `VELO_TASK_HOME` holds the per-run nonce in `VELO_TASK_TEST_ROOT_NONCE` (a test creates both, so nothing the environment alone controls, such as `TMPDIR` or the working directory, can grant it); otherwise a set value is refused (exit 2) on every invocation, never ignored. B5, B10, B16, B18-B19, B24-B25 and B28-B32 are driven by these seams; each cites the failpoint it uses.
- R22. **SessionStart and projection data.** SessionStart prints, in this order: in-flight rows (Vanth), open incidents (local), `pending`/`pending-unsent` records (local); each line `<kind> <job_id> <name> <verdict-or-status> <copy-paste command>`. Projection keeps one marker file `<state>/project/<job_id>` holding the GitHub comment id of the terminal comment, written after a successful post and consulted before posting, so a retry never double-posts; it never affects a verdict or a Stop decision.
- B33. **Hardening**: each of the six in-flight statuses blocks Stop; a `failed` row with a restart pending blocks; an unreadable database with an existing state directory blocks and `stop-override` releases once and logs; a stale `ack --job` (row changed) exits 2 and leaves the incident open; allowlist rejects `PYTHONPATH`, `DYLD_INSERT_LIBRARIES`, `PATH`, `VANTH_DAEMON_PORT`; two concurrent `run` calls with the daemon down start one daemon; a reused pid is not signalled; two creators plus an ack plus a gc on one job leave a consistent state at every failpoint; a collected job reads `unknown-job`; `wait --all` over `failed(42)` + `timeout` exits 1 and lists both; tombstone retirement survives a clock change. *Mutants: Stop covers three statuses; fail-open; ack without CAS; allowlist accepts any key; no daemon lock; clock-based tombstone; gc leaves index lines.*
- R23. **Projection v2: the pipeline mirrored into GitHub (ledger only).** Applies to jobs tagged `issue:N` (and `pr:M` once a PR exists); it extends R13 and obeys all of it: runs in `velo-task project`, never inside a verdict or Stop path, each `gh` call under `timeout 10`, a failed call leaves `proj-pending` and changes nothing, GitHub is never read to decide anything. (f) *Rate limits:* a `gh` call that fails with a rate-limit or 5xx is retried only on the next `project` invocation, never in a loop; at most one status-comment edit per issue per 30 s.
